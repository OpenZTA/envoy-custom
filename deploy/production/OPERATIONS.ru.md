# Эксплуатация OpenZTA Proxy

## Авторизация и время отзыва

Новый запрос или туннель проходит проверку до передачи данных приложению. Открытая сессия проверяется с заданным `recheck.interval` и `jitter`. При ошибке авторизации соединение закрывается; backend не получает разрешение по устаревшему кэшу.

RPC timeout задаётся отдельно от интервала повторной проверки. В примере он равен 2 секундам. Для соединения с NAC через WAN бюджет выбирают по измеренной задержке с запасом; удалённый LAB с SSH/mTLS-мостом использует 10 секунд после измерения задержки при одновременных TLS-подключениях. Увеличение бюджета увеличивает верхнюю границу реакции на отказ NAC, поэтому после изменения обязательно проверяются отзыв и недоступность авторизации. Разрешение при ошибке не включается. При транспортном отказе первоначального вызова NAC Envoy формирует HTTP 503 локально: заголовок X-OpenZTA-Reason может отсутствовать, а access log содержит response_code_details=ext_authz_error. После начала SSE/gRPC/WebSocket/WebTransport повторный HTTP-ответ не отправляется: закрывается существующий поток, причина фиксируется в журнале.

Практический верхний предел обнаружения изменения — интервал плюс jitter, время RPC и задержка планирования. Это измеряется на конкретном стенде. Таймер не является обещанием мгновенного отзыва. Для строгого SLA выбирайте интервал с учётом нагрузки на NAC и проверяйте p95/p99 времени отзыва под нагрузкой.

`max_session_duration: 0s` разрешает сессию без прикладного срока. Политика, срок сертификата, отказ транспорта и остановка экземпляра продолжают действовать. QUIC keepalive поддерживает тихую сессию при отсутствии прикладных сообщений.

Для WebTransport политики управляют сессией и всеми её потоками. Это не интерпретатор произвольного прикладного формата внутри потока. Содержательные ограничения SQL/команд/сообщений требуют соответствующего протокольного обработчика приложения или специализированного фильтра.

Для TCP карта ресурсов NAC использует фактический порт слушателя внутри контейнера. Назначение из заголовка PROXY v1/v2 не меняет ресурс авторизации: первоначальная и повторные проверки используют `directLocalAddress()`. При публикации порта или подключении L4-балансировщика указывайте в `PORT_MAPPING` внутренний порт слушателя.

## Наблюдаемость

Сохраняйте JSON access logs вместе с журналом решений NAC. Основные поля: session ID, resource, протокол, код ответа, response flags/details, продолжительность и fingerprint клиентского сертификата. Приватный ключ, полный сертификат и Authorization в журналы не добавляются.

Собирайте через внутренний admin endpoint `/stats/prometheus`:

* `openzta.continuous_authz` — первоначальные и повторные проверки, отказы и недоступность;
* `cluster.ext_authz` — ошибки соединения, `upstream_rq_timeout`, очередь и задержка NAC;
* HTTP/2, HTTP/3 и QUIC — resets, handshake failures, активные соединения;
* circuit breakers, overload manager, RSS/heap и рестарты контейнера;
* application-level события LAB — потоки, FIN/reset, дейтаграммы, дубликаты, перестановки, счётчики и время жизни.

Передавайте метрики через внутренний collector или sidecar с доступом к Unix socket. Admin socket даёт административные права и не предназначен для пользовательского доступа.

Настройте оповещения на появление authz timeout, рост отказов unavailable, OOM/restarts, срабатывание overload, увеличение незавершённых запросов и приближение срока сертификатов. Порог задержки NAC должен оставлять запас до RPC timeout. Обычные policy-denied и сбои инфраструктуры учитываются раздельно.

## Сертификаты и DNS

Новые сертификаты сначала проверяются вне обслуживающего экземпляра: цепочка, SAN, EKU, совпадение ключа, срок действия и доступность файлов runtime UID. Затем запускается новый экземпляр и выполняется mTLS-приёмка. В этом статическом профиле обновление файлов сертификатов само по себе не является подтверждённой ротацией работающего TLS context.

Для замены CA используйте период перекрытия доверенных корней. Сначала добавьте новый доверенный корень, затем замените сервисные сертификаты, проверьте клиентов и удалите старый корень. Отзыв клиентского сертификата проверяется NAC и на уже открытых сессиях.

Кластеры NAC и WebTransport используют bounded DNS refresh и быстрый failure refresh. При смене IP проверяйте восстановление без перезапуска прокси. Во время недоступности авторизация должна оставаться fail-closed.

## Несколько экземпляров и обновление

Каждый экземпляр самостоятельно проверяет политики и хранит состояние своих сессий. Доступность NAC, PKI и приложения обеспечивается инфраструктурой платформы.

Для HTTP/3/WebTransport входной балансировщик должен сохранять привязку QUIC-соединения к экземпляру. Предпочтителен QUIC-aware L4-балансировщик с маршрутизацией по Connection ID. Обычный UDP round-robin по пакетам непригоден. Проверка двух экземпляров по отдельности не проверяет поведение внешнего балансировщика при NAT rebinding или миграции клиента.

`prepare.py` записывает SHA-256 bootstrap в метку сервиса Compose. Изменение bootstrap после повторного preflight поэтому приводит к созданию нового контейнера. Для управляемого обновления с сохранением текущих сессий используйте отдельный экземпляр и drain; замена контейнера с тем же именем не переносит соединения.

Порядок обновления:

1. Сохраните предыдущий неизменяемый image digest, bootstrap и манифест. PKI хранится отдельно.
2. Подготовьте новый экземпляр через preflight, проверьте `/ready`, клиентский mTLS, новую авторизованную сессию и отказ неавторизованной.
3. Добавьте его в L4-балансировщик. Проверьте HTTP/2, HTTP/3, WebTransport и настроенные туннели через публичный путь.
4. Уберите старый экземпляр из выбора для новых соединений, сохранив доставку пакетов существующих QUIC-соединений.
5. Запустите drain старого экземпляра:

   ```sh
   docker compose -p openzta-proxy-old -f old/compose.json exec -T proxy \
     curl --fail --silent -X POST --unix-socket /tmp/envoy-admin.sock \
     'http://localhost/drain_listeners?graceful&skip_exit'
   ```

6. Дождитесь завершения активных сессий в пределах согласованного окна. Бессрочные сессии требуют конечного окна обслуживания и повторного подключения клиента. После окна остановите старый экземпляр.

HTTP/3 hot restart в этом профиле не используется. Активное QUIC-соединение не переносится между процессами. Клиент бизнес-приложения должен корректно обрабатывать закрытие и повторно авторизованное подключение.

Возврат версии выполняется тем же порядком с предыдущим digest и bootstrap. Политики и список отозванных сертификатов не откатываются вместе с бинарником. При возврате проверьте, что старый бинарник понимает конфигурацию; новый runtime-флаг или маршрут может потребовать старой версии bootstrap.

## Приёмка нагрузки

Отдельно измеряйте короткие запросы, число тихих соединений, число потоков, полезный трафик, дейтаграммы и стоимость повторной авторизации. Для смешанного WebTransport EPS задаётся на каждую выбранную передачу; суммарное число сообщений выше числа итераций.

Снимайте показатели до нагрузки, на плато и после закрытия сессий. Проверяйте, что очереди ограничены, активные сессии освобождаются, память стабилизируется, а policy revoke работает при медленном читателе и перегрузке. Перед обновлением лимитов повторите проверку отказа NAC и нового подключения при отозванном доступе.

Проверки на конкретной архитектуре и стенде подтверждают описанную конфигурацию и измеренную нагрузку. Значения пропускной способности для другой машины определяются её приёмкой.
